# pip, venv and the lock files

## 1. What it is

`venv` creates a **virtual environment**: a private folder (`.venv/`) holding its own Python and its own installed packages. `pip` is the installer that fills it. A **lock file** lists every package with an exact version and a hash, so every machine installs the same bytes.

## 2. Why this repository uses it

Every machine, and CI, installs the same bytes of the same tools, so "works on my machine" differences do not hide a failure.

## 3. Where it appears

| File | What it does with this technology |
| --- | --- |
| `Makefile (`$(STAMP)` target)` | creates `.venv` and installs the hash-checked lock |
| `requirements.lock, requirements-dev.lock` | runtime (`pyyaml`) and dev (pytest, ruff, mypy, yamllint ...) packages with hashes |
| `pyproject.toml` | the human-written dependency list with exact versions |

## 4. How it works underneath

- `python3 -m venv .venv` copies or links an interpreter into `.venv/bin/` and gives it its own `site-packages` folder. Running `.venv/bin/python` uses only what is installed there.
- `pip install --require-hashes -r file.lock` refuses any file whose SHA-256 hash is not listed. That blocks a swapped or tampered package.
- The lock files are generated from `pyproject.toml` by `uv pip compile --generate-hashes`; `pyproject.toml` lists what is wanted, the lock lists exactly what was resolved, including indirect dependencies.
- The Makefile uses a **stamp file** (`.venv/.installed`) as a target: when the lock changes, the stamp is older, so Make rebuilds the environment.

## 5. Walkthrough of this repository's use

```make
$(STAMP): requirements-dev.lock pyproject.toml
	$(PYTHON) -m venv $(VENV)
	$(VENV)/bin/pip install -q --require-hashes -r requirements-dev.lock
	touch $@
```
`venv` makes `.venv`. `pip install -q` (quiet) `--require-hashes` (every line of the file carries `--hash=sha256:...`; pip refuses anything else, and refuses indirect dependencies that are not listed) `-r` (read the list from a file). The lock file is generated by `uv pip compile --generate-hashes` from `pyproject.toml` and lists direct and indirect packages, so nothing is resolved on your machine. `make audit` then runs `pip-audit --require-hashes -r requirements-dev.lock` to look for known vulnerabilities in exactly those packages.

## 6. Try it yourself

1. `make install` : creates `.venv/` (about a minute the first time).
2. `.venv/bin/pip list | head` : only the locked packages.
3. `head -5 requirements-dev.lock` : lines like `pytest==9.0.2 \` followed by `--hash=sha256:...`.
4. `make audit` : checks for known vulnerabilities.
5. `.venv/bin/python -c "import sys; print(sys.prefix)"` : the `.venv` path, proving the isolation.

## 7. Mistakes people make

- Editing a lock file by hand; regenerate it instead.
- Mixing system-wide installs and the venv.
- Installing without hashes, so a changed upstream package goes unnoticed.

## 8. Check yourself

1. What is in `.venv/`?
   *Answer:* A private Python interpreter and its own installed packages.
2. What does `--require-hashes` protect against?
   *Answer:* A package whose bytes differ from the ones that were locked.
3. What is the difference between `pyproject.toml` and the lock file?
   *Answer:* The first says what is wanted; the second records the exact resolved versions and hashes.
4. Why does the Makefile touch a stamp file?
   *Answer:* So Make can tell whether the environment is older than its lock file.
5. Should you edit a lock file by hand?
   *Answer:* No. Regenerate it with the lock tool.
